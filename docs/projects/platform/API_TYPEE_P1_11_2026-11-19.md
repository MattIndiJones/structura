# Contrats de réponse et client généré

État local au 19/11/2026. Ce chantier traite P1-11 de l'[audit technique du 16/11](../../audits/AUDIT_GLOBAL_TECHNIQUE_2026-11-16.md),
constat A4.

## Ce qui ne tenait pas

- **2 routes sur 458 déclaraient leur réponse** : `/api/parse` et `/api/price`.
- **Le front écrivait chaque appel à la main** : chemin, paramètres et champs lus, contre des formes
  que personne n'avait écrites.
- **Une dérive restait invisible** : un champ renommé côté serveur cassait un écran sans qu'aucun
  test ne le voie.

## Les routes retenues

Le classement des vingt routes les plus appelées vient d'un usage réel : le journal d'accès du
workspace Admin, 1 655 appels du 03 au 19/11. S'y ajoutent les routes de la file de pricing, que
le Pricer emprunte depuis P1-4. Cela fait 24 routes nouvellement documentées, plus les deux qui
l'étaient déjà.

| Domaine | Routes |
|---|---|
| Calendriers | `POST /api/schedule/generate`, `POST /api/calendar/resolve`, `GET /api/calendar/catalog` |
| Volatilité | `POST /api/volatility/validate`, `/left-wing`, `/calibrate` |
| Marché | `GET /api/finance/hist_prices`, `/hist_vol`, `/underlyings` |
| Pricing | `POST /api/price/in-life` ; `POST /api/price/jobs/{price,in-life,implied-funding}`, `GET` et `DELETE /api/price/jobs/{id}` |
| Compte | `GET /api/auth/me`, `GET /api/auth/options` |

| Autres | `GET /api/alerts`, `GET /api/amc/studies`, `GET /api/trading/relationships` |

Les modèles sont dans `backend/app/api/responses.py`.

- **Champs obligatoires et facultatifs** : un champ que la route écrit toujours est obligatoire ;
  un champ écrit seulement dans certains cas, ou lu dans une colonne qui peut être vide, a une
  valeur par défaut.
- **Blocs du moteur** : distributions, table de flux, dossier de calibration et contexte de marché
  sont typés comme objets, sans être dépliés.
- **Contrats ouverts** : quatre réponses (MtM, calibration, historique et marché réalisé) recopient
  telle quelle la provenance de leur source. Leurs champs lus par l'écran sont déclarés, et le reste
  est admis.

## Documenter sans changer la production

Chaque route déclare sa réponse par `responses=returns(Modèle)`. Cette déclaration alimente
seulement le schéma OpenAPI et laisse la réponse **inchangée à l'octet près**.

Un `response_model` sur une route existante aurait eu deux effets en production : il aurait filtré
chaque champ oublié par le modèle, et changé un type mal déclaré en erreur 500. Le premier aurait
fait disparaître un champ sans bruit, le second aurait interrompu un écran.

**La garantie vient des tests.** Avec `STRUCTURA_VALIDATE_RESPONSES=1`, chaque réponse JSON 2xx
d'une route documentée est contrôlée contre son modèle.

- **Activation** : la variable est posée par `backend/tests/conftest.py` et par l'instance des
  parcours de bout en bout.
- **Champs inconnus** : ils sont refusés.
- **Dérive** : une réponse qui s'écarte de son contrat devient une 500 qui nomme le champ, et le
  test qui l'a produite échoue.
- **Emplacement** : le contrôle vit dans la classe de route (`ContractRoute`, dans
  `api/contracts.py`). Il tient donc aussi dans les 57 fichiers de tests qui montent un routeur dans
  leur propre application.

## Le client généré

`scripts/generate_api_client.py` écrit `frontend/src/api/generated.js` à partir du schéma.

- **Fonctions** : une par route documentée, nommée d'après la fonction du serveur (`listDeals`,
  `getDeal`, `resolveBusinessDay`…).
- **Types** : en JSDoc, tirés des modèles ; l'éditeur les montre.
- **Refus** : une `ApiError` porte le message du serveur, le statut et le corps.
- **Contrôle de dérive** : `backend/tests/test_api_client.py` échoue dès que le fichier ne
  correspond plus au schéma.

Premiers usages, à comportement constant :

- le catalogue de sous-jacents (`data/commonUnderlyings.js`) ;
- la liste des deals du store ;
- les contreparties et les relations de l'onglet Deal.

Le reste des appels passe au client au fil des écrans touchés.

Après un changement de contrat :

```
.venv\Scripts\python.exe scripts\generate_api_client.py
```

## Vérification

- **Contrôle et client** : `test_api_client`, 9 tests.
  - dérive du client et publication des routes ;
  - réponse conforme intacte ;
  - champ en trop, champ disparu ou type changé : 500 qui nomme le champ ;
  - route sans contrat non contrôlée ;
  - réponse intacte hors validation.
- **Fichiers de tests qui appellent ces routes** : les 38 tournent en mode strict, et leurs réponses
  réelles valident les modèles. 896 tests y passent.
- **Ce que le mode strict a trouvé :**
  - un type mal déclaré : `developer_origin` de `/api/auth/me` est un objet, pas une chaîne ;
  - un défaut de branchement : dans `api/trading.py`, le modèle de réponse importé masquait le modèle
    de base du même nom, et la liste des relations aurait répondu 500.

  Les deux sont corrigés. Le modèle de réponse s'appelle maintenant `TradingRelationshipRow`, et
  aucune autre collision de nom n'existe dans les fichiers branchés.
- **Parcours de bout en bout** : 8 réussis en mode strict, sans aucune réponse hors contrat dans le
  journal de l'instance.
- **Frontend** : le client généré a 6 tests ; les fichiers des trois usages repris passent.
- **Non fait** : la suite backend complète n'a pas été relancée. Le passage nocturne l'exécutera en
  mode strict ; une route documentée appelée par un test hors de ces 38 fichiers y sera contrôlée à
  son tour.
